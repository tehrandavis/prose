## Goal

Tehran asked on 2026-11-15 for comments like Word's and Overleaf's, for Typst. A writer or a reviewer selects text and attaches a comment to it. The comment shows in the margin of Writing and Focus modes, beside the text it belongs to. Other people can reply. A comment can be resolved, reopened and deleted.

Three things were decided on 2026-11-15 and are not open:

1. A comment is anchored to a range of text and has replies, resolve and delete.
2. Comments are stored in the `.typ` file itself, as Typst comments. They travel with the file through Git and email. Typst ignores them, so the PDF never changes. A file beside the document was rejected, because a comment must not be able to separate from its text.
3. The hard rules hold. The text storage holds the full source: no attachment, no hidden character, no substituted text. Nothing touches `layoutManager`. Drawing happens in the `NSTextLayoutFragment` subclass and in the existing `drawBackground` highlight. Icons are Phosphor. The interface is English only.

## Terms

Earlier terms keep their meaning (block, active block, open block, rendered fragment, fold, margin mark, marker, focus block, dimmed). New terms:

| Term | Meaning |
|-|-|
| Comment | The new feature: one thread anchored to a range of text. It has a first entry and zero or more replies |
| Source comment | Any Typst comment (`//` or `/* */`) that is not part of a comment. The existing `comment` command (`⌘/`) makes one |
| Anchor | The range of source text a comment belongs to |
| Start marker, end marker | The two short block comments that mark where an anchor starts and ends, for example `/*<k3f9x2*/` and `/*k3f9x2>*/`. In this note, "marker" alone still has Phase 6's meaning (a character of markup syntax); a comment's markers are always called start marker or end marker |
| Id | Six characters that join a start marker, an end marker and the records of one comment |
| Record | One line comment that holds one entry of a comment: the first entry, a reply or a resolve event |
| Store | The run of records at the end of the file |
| Card | The view in the margin that shows one comment and its replies |
| Gutter | The strip to the right of the text column that holds the cards |
| Active comment | The comment whose card was clicked, or whose anchor holds the caret |
| Comment index | The list of the open file's comments, built from the syntax tree |
| Problem | Something that looks like part of a comment but does not form a whole one: a start marker with no end marker, a record with no markers, and so on |

## What the existing code gives

- **Comment nodes.** `SyntaxKind.lineComment` (81) and `SyntaxKind.blockComment` (82) are in the flattened tree that `SyntaxTree.nodes(in:)` returns. `SyntaxTree.edit` returns the range typst-syntax parsed again, so a reader of the tree can look only at what changed.
- **Faint markers.** `MarkerRanges.markerKinds` already holds `.lineComment` and `.blockComment`. A start marker or an end marker in an open block draws in the faint colour today, with no new code.
- **Spell check skips comments.** `SpellCheckRanges` lists `.lineComment` and `.blockComment` among the kinds it never reads.
- **Folds.** A run of comments with only blank lines between them is one fold with no setup line. It draws as a margin mark (`chat-text`) and takes no height (`WritingFolds.swift`, spec Section 5.4). The store is such a run.
- **Glyph boxes.** `WritingGlyphMap.selectionRects(for:)` turns source ranges into rectangles over a rendered block's glyphs. The selection highlight and the spelling underline use it. The editor draws the selection there in `drawBackground(in:)`, under the transparent images.
- **Rendering attributes.** `RenderingAttributes` writes the spelling state and the open block's colours without a change to the storage, and a full restyle keeps them.
- **Block kinds.** `Engine/RenderBridge/src/outline.rs` ignores comments when it decides a block's kind (`Run.significant` leaves them out), so a paragraph with a start marker in it stays a paragraph. One case goes wrong today; see decision 9.
- **Grouped edits.** `ManuscriptTextView.insertSnippet` makes its edit through `insertText(_:replacementRange:)` inside `beginUndoGrouping()`, so undo and redo deliver `textDidChange`. A comment action needs the same path for two or three ranges in one group.
- **Pickers in the command panel.** The citation picker (`WorkspaceCitations.swift`) is a searchable list inside the `⌘J` panel. A list of comments can be built the same way.
- **The margin.** The text column has at least 36 pt on each side (`ManuscriptLayout.minimumInset`). The floating toolbar is an AppKit view over the editor pane that refuses first responder.
- **Shortcuts in use.** `Command.directShortcuts` has no `⌘⌥M`. The Window menu has Minimize (`⌘M`) and no Minimize All. The `⌘J` root keys in use are `i`, `s`, `p`, `m`, `l`, `r`, `c`, `v` and `f`.
- **The count in the status bar.** `DocumentMetrics.count` counts the characters of the raw text that are not whitespace. Code and source comments count today.
- **Find.** The editor uses `NSTextFinder` on the source.

## What Typst does with a comment

These facts decide the format. Each one names its source.

1. **A comment is checked for before the mode.** `Lexer::next` tests `/` followed by `/` or `*` before it looks at the mode, so `//` and `/*` start a comment in markup, math and code (`crates/typst-syntax/src/lexer.rs`, lines 94 to 123).
2. **Block comments nest, and an open one runs to the end of the file.** `block_comment` counts depth and stops at the `*/` that closes the first `/*`. At the end of the file it returns with no error (`lexer.rs`, lines 160 to 183). So a `/*` whose `*/` is lost comments out the rest of the document, silently. A `*/` with no `/*` is an error token ("unexpected end of block comment").
3. **A line comment ends at a newline and nothing else.** `line_comment` reads until `is_newline`: LF, VT, FF, CR, U+0085, U+2028 and U+2029 (`lexer.rs`, lines 155 to 158 and 1144 to 1153). A `*/` or a `/*` inside a line comment has no effect.
4. **Raw text, strings, labels and links read their own characters.** `raw` reads to the closing backticks, `string` to the closing quote, `label` and `ref_marker` read label characters, and `link_prefix` accepts `/` and `*` as part of a URL (`lexer.rs`, lines 190, 1069, 575 to 597 and 1156 to 1187). A `/*…*/` inside raw text or a string is text and would print. A `/*…*/` directly after a bare URL becomes part of the link.
5. **In markup, text stops before a comment.** `text` stops at a `/` that is followed by `/` or `*` (`lexer.rs`, lines 618 to 628). `word/*c*/word` is text, comment, text.
6. **Comments produce no content.** `SyntaxKind::is_trivia` covers both comment kinds (`crates/typst-syntax/src/kind.rs`, line 369). `Markup::exprs` casts each child to an expression, and a comment casts to none (`crates/typst-syntax/src/ast.rs`, lines 233 to 245 and 378 to 383), so evaluation never sees it.
7. **Two pieces of text with the same style are shaped as one.** The inline collector merges adjacent text segments with equal styles into one segment (`crates/typst-layout/src/inline/collect.rs`, lines 281 to 287). So a comment in the middle of a word should not break a ligature, kerning or hyphenation. Proved in step A: `fi`, `ff` and `ffi` ligatures, a kerning pair, hyphenation and Arabic joining are unchanged by a start marker inside the word.
8. **A space beside a comment is a space element, not a space character.** Without a comment, `text` keeps a single space inside the text when a letter or digit follows (`lexer.rs`, line 623). With `quick /*c*/brown`, the space becomes its own node. Typst's realization turns a space element into the same U+0020 in the paragraph's text, and collapses two space elements into one (`crates/typst-realize/src/lib.rs`, the space handling near lines 1033 to 1113). Proved in step A: justified text over more than one page has the same glyph positions.
9. **The parser skips trivia before every token, in every mode, and some rules ask whether trivia was there.** `Parser::lex` collects spaces and comments before each token (`crates/typst-syntax/src/parser.rs`, lines 1854 to 1886). `directly_at` is false after trivia. So `@key/*c*/[p. 4]` loses its supplement (`parser.rs`, lines 215 to 222), and `#emph/*c*/[x]` is no longer a call with a content block. In math, `had_trivia` changes attachments and factorials (`parser.rs`, lines 333 to 413), and `ab` is one identifier while `a/*c*/b` is two (step A: `p/*c*/i` prints "p i", not π; `x/*c*/^2` and `n/*c*/!` did not change).
10. **A comment at the start of a line keeps the line's meaning but changes its column.** A heading, list, numbered or term marker counts when the trivia before it held a newline (`parser.rs`, `markup_exprs`, lines 50 to 62), so `/*c*/= Title` is still a heading. But a list item's nesting uses the column of its marker, and the column counts every character since the newline, the comment's included (`parser.rs`, lines 181 to 196 and 1689 to 1694; `lexer.rs`, line 67). A comment before `- item` moves the item's column by the comment's length. Step A: before a list, numbered or term marker the item nests; before a heading marker nothing changes.
11. **`*` and `_` look at their neighbours.** A `*` or `_` between two letters or digits is text; otherwise it starts strong or emphasis (`lexer.rs`, `in_word`, lines 640 to 656). A comment between a letter and a `*` changes the neighbour, so `word/*c*/*x*` is strong where `word*x*` is text. A comment directly after any `*` is worse: the lexer reads `*/` as a stray end of comment, a compile error, so `*bold*/*c*/` and `*/*c*/bold*` do not compile (found in step A). The same kind of change happens inside a shorthand (`--`, `...`) and after `=`, `-`, `+` and `/`, because `space_or_end` treats a following `/*` as a space (`lexer.rs`, lines 658 to 665).
12. **A space after a statement is dropped, and a comment in between keeps it.** `Markup::exprs` drops a space that directly follows `#let`, `#set`, `#show`, `#import` or `#include`. A comment between the statement and the space resets that test (`ast.rs`, lines 234 to 243). The syntax tree does not show this difference. Step A: it shows only for a comment at the end of the statement's line (`A#let x = 1/*c*/`, a line break, `b` gives "A b", not "Ab"); other text after the statement on its line is a compile error with or without a comment.

Everything this section left open was checked in step A; see "Step A outcome".

## Decisions

### 1. The format: two short inline block comments and a store of line comments

A comment in the source looks like this:

```typst
The /*<k3f9x2*/quick brown fox/*k3f9x2>*/ jumps over the lazy dog.

More text.

// prose:comments 1
// prose:comment k3f9x2 | Tehran Davis | 2026-11-15T14:02:11Z | Is "quick" the right word here?
// prose:reply k3f9x2 | Ada Park | 2026-11-15T15:10:40Z | Yes. Compare the first chapter.\nA second paragraph.
// prose:resolve k3f9x2 | Tehran Davis | 2026-11-16T10:00:03Z
```

**Start marker and end marker.** The start marker is `/*<` + id + `*/`. The end marker is `/*` + id + `>*/`. Each is 11 characters. They hold nothing but the id, so no text a person writes can ever be inside a block comment. That matters because of fact 2: text with `*/` or `/*` in a block comment could end it early or comment out the rest of the file.

**Id.** Six characters from `abcdefghjkmnpqrstuvwxyz23456789` (31 characters; no `i`, `l`, `o`, `0` or `1`), the first one a letter. Prose makes an id at random and checks that the file does not have it. There are about 660 million ids. If two Git branches each add 100 comments, the chance that any two ids collide is about 1 in 66,000.

**Records.** Each record is one line comment that starts at the first column:

| Record | Form |
|-|-|
| First entry | `// prose:comment <id> \| <author> \| <date> \| <text>` |
| Reply | `// prose:reply <id> \| <author> \| <date> \| <text>` |
| Resolve event | `// prose:resolve <id> \| <author> \| <date>` |
| Header | `// prose:comments 1` |

The fields are divided by a space, a bar and a space. The date is UTC, ISO 8601, to the second. The text is the last field, so it may hold bars. The header gives the format version and is the first line of the store.

**A comment is resolved when it has a resolve record.** Reopen removes the record. The other choice is a state word in the first entry. A record of its own is better for Git: to resolve is to add a line, not to change one, and the record says who resolved it and when.

**Replies have no id.** A reply is its line. Edit and delete change or remove that line. Nothing refers to a reply from another place.

**Where records go.** Prose reads a record wherever a line comment at the top level of the file starts a line. Prose writes records into the store: the last run of records in the file, after one blank line. If the file has no store, Prose adds a blank line, the header and the record at the end of the file. Each file has its own store, so an included chapter carries its own comments.

**Choice: Prose keeps the store in id order, with one comment's records together and its replies in date order.** Ids are random, so two branches that each add a comment usually insert at different lines, and Git merges both with no conflict. With date order, every new comment goes on the last line, and two branches that each add one always conflict. The cost of id order: the store does not read in document order. A person reads comments in the cards, not in the store, so I recommend id order.

**Why this format.** It meets each need in the brief:

| Need | How |
|-|-|
| Marks the start and end inline, inside a paragraph, across inline markup and across blocks | Two independent block comments. Neither one has to pair with the other in Typst's grammar, so an anchor can start in one block and end in another |
| Carries id, author, date, text, replies and resolved state | Records |
| Valid Typst, same PDF | Facts 5 to 8, with the placement rules of decision 2; proved in step A |
| Readable in Code mode | The paragraph gains 22 characters per comment. The text of the comment is in one place, one entry per line, in plain words |
| Survives another editor | Line comments cannot damage the document whatever happens to them (fact 3). A lost record leaves two harmless 11-character comments |
| Survives Git merges | One entry per line; a reply and a resolve add lines and never touch the paragraph, so a reviewer's reply does not conflict with the author's edit of the same paragraph |
| Quiet in the open block | 11 faint characters at each end of the anchor, and no comment text |

**Alternatives, and why they lose.**

1. **Everything inline.** The start marker carries the whole thread: `/*prose k3f9x2 {"author":…,"text":…}*/quick brown fox/*k3f9x2*/`. The comment can never separate from its text, even in a cut and paste into another editor. It loses for four reasons. The open block cannot hide characters, so a 300-character thread would sit in the middle of the sentence the writer is working on. Code mode becomes hard to read. Every reply and every resolve changes the paragraph's line, so it conflicts in Git with any edit of that paragraph. The text of a comment would be inside a block comment, where a `*/` or `/*` that an escape misses comments out the rest of the document (fact 2).
2. **Records as one block comment at the end** (`/* … */` with one entry per line). It looks tidier. It loses because of fact 2: the text must be escaped for both `*/` and `/*`, and one escape that is missed ends the block early. If the opening `/*` is lost (a merge that goes wrong, a careless edit), every record becomes paragraph text that prints, and the closing `*/` is a compile error. Line comments have no such failure: a damaged line harms only itself.
3. **Records beside the anchor.** A line comment on the line after the paragraph that holds the start marker. The record moves with its paragraph when a writer moves the paragraph in any editor. It loses because the position after a paragraph is not always markup: an anchor inside a figure caption, a table cell or a footnote is inside a function call's arguments, where a line comment would sit in code, and in a list a line comment changes which line continues an item (fact 10). The rule for where the record goes would have many cases, and each case is a way to change the PDF.
4. **A Typst function.** `#let comment(id: none, body) = body` in the preamble and `#comment(id: "k3f9x2")[quick brown fox]` in the text. Tools would see real structure. It loses because it is not a comment: the file needs the definition to compile, a content block cannot start in one paragraph and end in another or cross the edge of `*strong*`, and wrapped text can change show rules and layout. It also goes against the decision of 2026-11-15.
5. **Line comments for the start marker and the end marker.** A line comment ends only at a newline, so each one would force a line break into the paragraph. A newline is a space in Typst, so an anchor could not start in the middle of a word, and the paragraph's lines in the source would change shape.

### 2. Where a comment may be anchored

The rule is in two parts: a list of places, and a check that Prose runs on every new start marker and end marker.

**Places.** A start marker or an end marker may stand only in markup: between two children of a markup node, or inside plain text. Markup includes the content blocks of calls, so an anchor can be inside `#emph[…]`, a footnote, a figure caption or a table cell written as `[…]`.

| Position | Allowed | Reason |
|-|-|-|
| Between words, or inside a word, in a paragraph, heading, list item or term item | Yes | Facts 5 to 8 |
| Across `*strong*` or `_emphasis_`, with one end inside and one outside | Yes | The two are independent |
| From one block to a later block | Yes | The two are independent |
| Around a whole inline or display equation, raw span or raw block, citation with its supplement, label, `#link(…)[…]` call, or other call | Yes | Both are outside the node |
| Directly after a bare URL (`https://typst.app/*id>*/`) | No | Fact 4: the URL reads the end marker into itself, a compile error. The end marker goes after the next space, or the anchor ends before the URL |
| Directly after a `*`, whether it opens strong text, closes it or is plain text | No | Fact 11: a compile error. A start marker goes before the `*`. An end marker goes before the closing `*` (`*bold/*id>*/*`), so the marked words are the same |
| Inside math | No | Fact 9. The whole equation can be inside an anchor |
| Inside raw text or a string | No | Fact 4: it would print |
| Inside a label, a reference, a link, an escape or a shorthand | No | Facts 4 and 11 |
| Inside code: a call's name, its parenthesised arguments, a code block | No | Fact 9, and version one keeps out of code |
| Between a call or a reference and what attaches to it (`#f` and `(`, `#f(x)` and `[`, `@key` and `[`, `#x` and `.y`) | No | Fact 9 |
| Before a line's list, numbered or term marker, or in the indent of a list item's later lines | No | Fact 10. The start marker goes after the marker and its space: `- /*<id*/item`. Prose puts it after a heading marker too, though step A found that harmless before one |
| At the end of the line of a `#let`, `#set`, `#show`, `#import` or `#include` statement | No | Fact 12 |
| Next to a `*` or `_`, a shorthand or a line-start character where it changes what that character means | No | Fact 11; found by the check |

**The check.** Before Prose writes a start marker and an end marker, it parses the block's text with both in place and compares the flattened tree with the tree before, without the two new comment nodes and with offsets moved. `SyntaxTree` leaves text and space nodes out of the flattened tree, so a word cut in two does not count as a change. If any other node differs, the position is not safe.

**Snapping.** Prose first trims whitespace from the selection, then moves each end to the nearest allowed place: an end inside a node from the "No" rows moves outward to that node's edge, so the anchor only grows. The one exception is an end marker after a closing `*`, which moves inside it. If the check still fails, or an end cannot move within its block, Prose makes no change and says "Prose cannot attach a comment to this selection" in the window's message line.

**Images and other blocks with no text.** A comment on a figure anchors the whole call: `/*<id*/#figure(…)/*id>*/`. Comments on a part of an image are out of scope.

**Empty selection. Choice:** Add Comment with a caret and no selection anchors the word at the caret, as Word does. With no word there, it does nothing.

**Anchors may overlap and nest.** Each comment has its own id, so nothing stops two anchors from sharing text.

### 3. Escaping and limits

- **Text.** In a record, a backslash is written `\\` and a line feed `\n`. CR LF becomes `\n`. The other characters that Typst reads as a newline (fact 3: VT, FF, CR, U+0085, U+2028, U+2029) are written `\u{…}` with the code point in hex, and Prose reads `\u{…}` for any code point. Every other character is written as it is, in UTF-8. `*/`, `/*`, `//` and `|` need no escape (fact 3, and the text is the last field). A backslash before any other character is not valid.
- **Author.** One line, no bar, no newline character, whitespace trimmed, at most 64 characters. Prose removes what does not fit when it reads the setting.
- **Whitespace.** Prose trims whitespace at the end of a record's text, because many editors strip it from line ends.
- **Limits.** Prose writes at most 4,000 characters of text per entry and at most 200 replies per comment, and says so when a writer reaches either. It reads records of any length.
- **Non-ASCII.** Ids and keywords are ASCII. Authors and text are any Unicode.
- **A malformed part is a source comment.** Prose never guesses. The index lists each of these as a problem, with its line, and changes nothing by itself:

| What the source holds | What Prose shows |
|-|-|
| A block comment that is not exactly a start marker or an end marker (wrong length, a character outside the alphabet, a space) | A source comment. Not a problem, because a writer may write `/*<note*/` |
| A start marker and an end marker with no first entry | Two source comments, and a problem: "Markers with no comment". Action: Remove Markers |
| A first entry with one of the two, or with the end marker before the start marker | No highlight. The card sits at the one that exists, with "The marked text is damaged". Actions: Attach to Selection, Delete |
| A first entry with neither | No highlight. The comment is in the list under "Not attached". Actions: Attach to Selection, Delete |
| An id with two start markers, two end markers or two first entries (a copy made in another editor, or a merge) | No highlight for that id, and a problem: "Used more than once". Actions on each copy: Give a New Id, Remove |
| A line that starts `// prose:` and does not parse | A source comment, and a problem: "Unreadable comment line" |
| A reply or a resolve record whose id has no first entry | A problem: "Reply with no comment". Action: Remove |
| A header with a version above 1 | Prose shows the comments it can read, makes every comment action unavailable in that file, and says a newer Prose wrote them |
| A block comment that never closes (fact 2) | Not Prose's to repair: the rest of the file is a comment, and the index reports the start marker or the end marker it began with as "Not closed" |

### 4. Anchors and edits

The start marker and the end marker are text. An edit inside the anchor moves the end marker with it, and an edit before the anchor moves both. No offset is stored anywhere.

**Every comment action is an ordinary undoable edit of the source.** Add, reply, edit, resolve, reopen and delete each make their replacements through the editor's native edit path, in one undo group with its own action name ("Add Comment", "Reply to Comment", and so on). `⌘Z` in the editor takes the whole action back. Nothing else is stored: no file beside the document, no entry in `recent.json`.

**Edits by the writer in Prose.** These rules apply in every mode. They run in one place, the editor's gate for text changes (`shouldChangeText(in:replacementString:)`), so typing, Delete, cut, paste over a selection and a drop all get them. Step C chooses between a rewrite of the edit and a second edit in the same undo group. Neither runs while text is marked, during undo or redo, or for a change that comes from the disk.

| The writer's edit | Result |
|-|-|
| Removes text that holds the start marker and the end marker of one comment | The comment is deleted: its records go in the same undo step. This is what Word does. **Choice**; the other choice keeps the comment with an empty anchor |
| Removes text that holds one of the two | That one stays, at the place of the removal, so the anchor shrinks and the comment lives |
| Removes all the text between the two, but neither of them | The comment stays with an empty anchor. Its card says "The marked text was deleted" |
| Backspace or Forward Delete directly beside a start marker or an end marker, with no selection | The key passes over it and removes the next character of text. Neither can be deleted by a single key |
| Types or pastes directly before a start marker or after an end marker | The new text is outside the anchor. Directly after a start marker or before an end marker, it is inside. The caret is where it is |

**Choice: in Writing and Focus modes, Left and Right pass a start marker or an end marker in one step.** Eleven key presses to pass a faint mark would be a defect. There are two caret stops, one on each side, and in the open block the writer can see which side the caret is on. Shift with the arrows does the same. In Code mode the arrows move by character, as for all source.

**Copy, cut and paste. Choice:** the plain text that Prose puts on the pasteboard has no start marker and no end marker, so text pasted into an email or another app is clean. Prose also writes a private pasteboard type that holds the exact source and the records of every comment whose start marker and end marker are both in the selection. A paste in Prose reads the private type:

- After a cut, the ids are gone from the file, so the paste brings the start marker, the end marker and the records back with the same ids.
- After a copy, the ids are still in the file, so the paste gives each comment a new id and a copy of its records. Word copies comments the same way.
- A paste into another file works the same way and adds the records to that file's store.
- A selection that holds one of the two (the anchor continues outside it) copies as text without it, and a cut follows the table above.

A paste is one undo step.

**Edits from outside Prose** (another editor, a merge, a change on disk) get no repair. The index reads what the source holds and reports problems as decision 3 says.

**Undo.** Undo and redo replay source states exactly. No rule above runs for them.

### 5. Author identity

- The author's name comes from one setting, **Name for comments**, in the Writing tab of Settings. Its default is the macOS full name (`NSFullUserName()`). An empty value falls back to the macOS full name, then to "Author". It is stored on this Mac and not synced.
- There are no accounts and no server. Prose does not enforce ownership: anyone who can edit the file can edit or delete any entry. Git records who changed what.
- A card shows each entry's author and date. The date is stored in UTC and shown in the Mac's time zone, as a short date ("15 Nov, 14:02").
- **Choice: no colour per author in version one.** Word gives each author a colour. With names on the cards it adds little, and the colours would need a rule that is stable across Macs. All anchors use one highlight colour.

### 6. How it looks

**The highlight.** The anchored text gets a fill under the glyphs.

- In a rendered block: `WritingGlyphMap.selectionRects(for:)` gives the rectangles, and `drawBackground(in:)` fills them under the transparent image, before the selection highlight, so a selection draws over a comment's highlight. This is the path the selection uses today.
- In the open block, in other source blocks and in Code mode: a background colour as a rendering attribute through `RenderingAttributes`, as the spelling state is written. The storage's attributes never change.
- A rendered block whose anchor has no glyph box (a figure with an image only) gets a 1.5 pt outline in the highlight colour around the block's image.
- An anchor inside a closed fold, a pill or a block that stays source over 400 lines has no highlight of its own until it opens; its card sits level with the row.
- **Choice: the colour is the warning amber `#E8A838`** at 28 percent in light appearance and 32 percent in dark, and at 50 percent for the active comment. Violet is the selection of the sidebar and reads as "selected". Amber is the one token that reads as "a note". Step C measures the contrast of body text on the fill and records it; it must stay 4.5:1 or better.
- A resolved comment has no highlight unless resolved comments are shown; then it has a 1 pt underline in the secondary text colour and no fill.

**Start markers and end markers.** In a rendered block they are invisible, because Typst does not draw them. In the open block they cannot be hidden, since the storage holds the full source, so they draw in the faint colour (the text colour at 40 percent) in the document's font, as Phase 6 draws every marker. `MarkerRanges` already does this. In Code mode they have Tinymist's comment colour.

**The store.** In Writing and Focus modes the store is a fold with no setup line. **Choice: the store's fold draws no margin mark and takes no height.** A `chat-text` mark at the end of every commented file would look like a source comment and invite a click that shows raw records. The fold opens when the caret goes inside it, or through **Show Comment Source** (`⌘J K U`), and it follows the fold rules otherwise. One exception to those rules: an edit that a comment action makes inside the store does not open the fold. In Code mode the store is plain source.

**Cards.**

- A card shows the first entry's author (13 pt semibold) and date (11 pt, secondary text), then the text (13 pt). Replies follow under a hairline, each with author, date and text. The active card adds a **Reply** field, a **Resolve** button (`check-circle`) and a menu (`dots-three`) with Edit and Delete for each entry.
- A card is 224 pt wide, in the panel colour with a hairline border and no shadow. The active card's border is the accent colour. **Choice: radius 8 pt**, the floating toolbar's radius. The spec gives cards 14 pt, which is too round for a card this small.
- Icons are Phosphor Regular at 16 pt. Step D adds the icons the bundle lacks (`chat-circle`, `check-circle`, `arrow-bend-up-left`, `pencil-simple`, `trash`, `dots-three`). The toolbar and the cards use `chat-circle`, so `chat-text` keeps one meaning, a source comment's margin mark.

**Where the cards live. Choice: an AppKit view over the editor pane, a sibling of the scroll view, with one hosted SwiftUI view per visible card.** It is outside the text view and outside the text system, so no hard rule applies to it. It moves its cards when the clip view's bounds change, in the same turn of the run loop. It makes views only for comments whose anchors are in or near the viewport. The other choice is to add the cards as subviews of the text view. They would scroll with no code, but they would be inside the text view's accessibility children, its hit testing and the pixel tests that use `cacheDisplay`. I recommend the sibling.

**Position and stacking.** A card's top is level with the top of its anchor's first drawn line: from the glyph boxes in a rendered block, from TextKit's segment frames in source. Cards stack in document order and never overlap: each card's top is the lower of its anchor's line and the card above plus 8 pt. The active card always sits level with its anchor, and the cards above and below it move away to make room.

**The gutter and narrow windows.** The gutter is 240 pt wide, 12 pt right of the text column.

| Editor pane | Layout |
|-|-|
| Wide enough for the centred column and the gutter | The column stays centred and the gutter is to its right |
| Not wide enough for that, but wide enough for the column, a 36 pt left margin and the gutter | The column moves left, as far as the 36 pt margin, to make room. The column's width does not change, so nothing renders again |
| Narrower than that (a small window, or the preview pane open) | No gutter. Each comment draws a `chat-circle` icon in the right margin, level with its anchor. A click opens the card in a popover. The highlight stays |

The gutter is there only while comments are shown and the file has a comment to show. Whether it is there changes only when a comment is added, removed, resolved or shown, never while the writer scrolls.

**The preview pane** shows the PDF, which holds no comments. It shows nothing of them.

**Focus mode.** Focus hides the sidebar and the preview, so the 467 pt column usually has room for the gutter. **Choice: Focus shows cards only for comments whose anchor touches a focus block.** Other comments draw a `chat-circle` icon in the right margin at 45 percent, and their highlight dims with their block, as spelling underlines do. Cards do not fade while the writer types. The other choice shows every card dimmed; a column of dimmed cards beside dimmed text works against what Focus is for.

**Code mode. Question:** do cards show in Code mode? The overlay and the highlight work there with no more code, since Code mode is source and the highlight is a rendering attribute. I recommend yes, with the same **Show Comments** switch, because a writer who reviews in Code mode should see who said what without reading the store. The other choice is source only, which keeps Code mode as plain as it is today.

**Dark appearance.** Cards use the dark panel tokens. The highlight uses the dark amber value above. No colour in a rendered block's image changes.

### 8. Interactions

- **Spell check.** Start markers, end markers and records are comments, so `SpellCheckRanges` skips them. A word that an anchor cuts in two (`un/*<id*/believable`) is not checked, by the existing rule for words that markup cuts. Text in a card's field is checked by the field's own `NSTextView` spell checking, which is right there because that text is plain words.
- **Find and replace.** Find searches the source. Two effects follow. A match in a record opens the store's fold, as a match in any fold does. A phrase with a start marker or an end marker inside it is not found: "quick brown" does not match `quick /*<k3f9x2*/brown`. A fix needs an `NSTextFinderClient` that gives find a text without the two and maps ranges back. **Choice: version one accepts this limit** and the writing guide names it. Step E measures how much work the client is, and Tehran decides then.
- **Citations.** A citation inside an anchor needs nothing. An anchor that ends at a citation ends after its supplement, by decision 2. The citation picker and every other insertion treat a start marker or an end marker as a word boundary: `CitationInsertion.text` adds its space as it does beside any character that cannot join a key. The inserted text goes where the caret is, inside or outside the anchor.
- **Block boundaries.** A start marker or an end marker inside a paragraph, a list or an equation block is already ignored when the engine decides the block's kind. One case is wrong today. An end marker at the end of a heading line is outside the heading node, because `Parser::wrap` stops before trailing trivia (`parser.rs`, lines 1785 to 1790), and `split_tree` in `outline.rs` then starts a new block that holds only that comment. Writing mode would draw a margin mark after the heading. Step A changes `split_tree`: a comment on a heading's line, before or after its label, belongs to the heading's block. The C ABI does not change. A start marker or an end marker alone between two blank lines is a comment block and draws as a margin mark; that is what the source says.
- **Rendering.** A block's render compiles the block's source with its comments, and Typst ignores them. Glyph boxes carry real source offsets, so they stay right. Adding a comment changes the block's text, so that block renders once more.
- **Export.** PDF export is unchanged. Step A proved the PDF bytes identical for every allowed position, apart from the creation date and the document id made from it, which differ between any two exports. **Copy Source Without Comments** writes a copy of the open file with every start marker, end marker and record removed, to a place the writer chooses. It never changes the open file. Source comments stay. It covers the open file only in version one.
- **Tinymist.** Comments give no diagnostics. Semantic tokens colour them as comments. The formatter (`textDocument/formatting`, Tinymist's default) was run in step A. It never changes the output. It adds one space after a start marker that is first in a heading's or list item's text (`= /*<id*/ Title`) and around a term's text, and it trims trailing spaces in records. It leaves other start markers, end markers and the store alone. So the highlight never covers whitespace at an anchor's edges, and Copy Source Without Comments removes such a space with the start marker.
- **Word count.** A start marker, an end marker and the store do not count. The index knows their characters, and the count in the status bar subtracts them. Source comments count as they do today.
- **Document history, autosave, recovery.** Comments are source, so all three carry them with no change.
- **VoiceOver.** The editor's value is the source, so by default VoiceOver would read `/*<k3f9x2*/` as characters. The editor's attributed strings for ranges mark an anchor with the accessibility annotation attribute, with the label "Comment by Tehran Davis: Is quick the right word here?", so VoiceOver announces the comment where the anchor starts. The exact attribute key and what VoiceOver says for it are to verify in step E. The gutter is an accessibility group named "Comments" beside the editor. Each card is an element with its author, date, text and number of replies, and its buttons are children. Next Comment and Previous Comment work from the keyboard.
- **IME.** While text is marked, the index is not applied, no card moves and no rule of decision 4 runs.
- **Files changed on disk.** The index is rebuilt from the new text. Problems show as decision 3 says.

### 9. The comment index and its cost

- **What it is.** `CommentIndex` (ProseCore, pure) holds, for the open file, each comment's id, the ranges of its start marker and end marker, its entries, its state and its problems. It is built from the syntax tree's comment nodes and the source: a block comment of exactly 11 characters is tested against the two forms, and a line comment at the start of a line is tested for the prefix `// prose:`.
- **How it stays current.** On open, and after a change that replaces the text, the index is built from the whole tree off the main thread. On an edit, `SyntaxTree.edit` returns the range that was parsed again. The index drops its items in that range, reads the comment nodes of that range, and moves every later item by the edit's change in length. Entries are decoded only when a card needs them.
- **Estimate, to be measured in step B.** A build over a whole book is one pass over the comment nodes, well under the 0.1 s that the book's parse takes on open. An edit costs one window query over the parsed range, about as much as the marker ranges the open block already asks for, and one pass over the later items: for 1,000 comments, a few microseconds. The store is at the end of the file, so almost every edit moves all of its records; that is 1,000 additions.
- **Gate.** A copy of each book fixture with 500 comments spread through it runs the book benchmark in Writing mode. Typing p95 may rise by at most 0.5 ms against the same run without comments, on a quiet machine.
- **Cards and highlights.** Only anchors in or near the viewport are turned into rectangles. A scroll moves the existing card views and makes no new layout of text.

### 10. Out of scope for version one

- Tracked changes (suggestions to insert or delete text).
- Live collaboration, and any sync of comments to a service or a server.
- Comments on a part of an image, or on a region of the PDF preview.
- Anchors inside math, raw text, strings and code.
- A list of the comments of every file in a project. The index covers the open file.
- A colour per author, mentions, notifications and reactions.
- An edit history for an entry. Git has it.

## Acceptance tests

UI tests are `extension WritingFlowTests`, on the real window, editor and engine, and every test window goes through `placeOnTestScreen`. Each UI test also checks that the storage equals the source, that no attachment exists, that the undo stack is unchanged unless the test edits, and that TextKit 2 is still on.

**The format (step A)**

1. For every fixture, the laid-out pages with comments and without them are equal: the same pages, and on each page the same glyphs with the same fonts, sizes and positions, with no tolerance. The PDF bytes are compared too, and the outcome says whether they are identical.
2. For every "No" row of decision 2, a fixture shows the difference the row names (text that prints, a lost supplement, a changed list), so the rule has a test and not only a reason.
3. A heading with an end marker at its end, with and without a label, is one heading block, and no comment block follows it.

**The model (step B)**

4. Round trip: for text with every character of decision 3 (a backslash, each newline character, `*/`, `/*`, a bar, emoji, CJK), encode then decode gives the same text, and the record is one line that typst-syntax parses as one line comment.
5. For 1,000 random documents and random sequences of add, reply, edit, resolve, reopen and delete, the index after each action equals an index built from the new text, and the text with every comment removed equals the original document.
6. Anchoring: for each row of decision 2's table, a selection gives the expected start marker and end marker, the expected snap, or a refusal; the tree without the two equals the tree before.
7. Every row of decision 3's table gives the state and the problem the table names, and Prose changes no character of a malformed part.
8. The index after an edit equals an index built from the whole new text, for 10,000 random edits of a book fixture with 500 comments.

**Drawing and editing (step C)**

9. With `cacheDisplay`, an anchor inside a rendered paragraph has the highlight colour under its glyph boxes and nowhere else, across a line break and across a block boundary, in light and dark. The storage has no background attribute.
10. In the open block, the start marker and the end marker have the faint colour and the anchor has the highlight, and the storage's attributes equal Code mode's.
11. The store draws nothing and takes no height in Writing and Focus modes. A reply does not open it. The caret inside it opens it.
12. Left and Right pass a start marker and an end marker in one step in Writing and Focus modes. Backspace beside one removes the next character of text. A selection that holds both, deleted, removes the records in one undo step, and one undo brings everything back.
13. A deletion that holds one of the two leaves it at the place of the deletion, and the comment's anchor is the text that remains. The count in the status bar is the same with and without comments.

**Cards and actions (step D)**

14. Add Comment on a selection inside a rendered paragraph, with text posted, puts the start marker, the end marker and a record in the source as one undo step. One undo removes all three, and one redo returns them.
15. Three comments whose anchors are on one line draw three cards that do not overlap, in document order. The active card is level with its anchor.
16. Reply, edit, resolve, reopen and delete each change only records (delete also the start marker and the end marker), each as one undo step, and the card follows.
17. With the pane wide, the column is centred and the gutter shows. Narrower, the column moves left and its width is unchanged. Narrower still, with the preview open, icons replace the cards and a click opens a popover. No block renders again in any of the three.
18. In Focus, only the focus block's comments show cards, and the other comments' icons and highlights draw at 45 percent.
19. Next Comment and Previous Comment visit every comment in document order and wrap. The block stays rendered.
20. The author on a new comment is the setting's value, the macOS full name when the setting is empty, and never holds a bar or a newline.

**Interactions (step E)**

21. Copy of an anchored sentence gives plain text with no start marker and no end marker. Paste in the same file gives a second comment with a new id and the same entries. Cut and paste keeps the id. Each paste is one undo step.
22. A citation inserted by the picker at each edge of an anchor compiles, and the anchor still passes decision 2's check. An anchor made on `@key[p. 4]` ends after the supplement.
23. Copy Source Without Comments gives a file that has no start marker, no end marker and no record, keeps every source comment, and compiles to the same pages as the open file.
24. The editor's attributed string for a range that holds an anchor carries the annotation with the comment's author and text, and the gutter's cards are accessibility elements with their buttons as children.
25. A file changed on disk so that one end marker is gone shows the card with "The marked text is damaged", no highlight, and no change to the source.

**Performance (steps C, D and F)**

26. The book benchmark runs in Code, Writing and Focus on SICP and War and Peace and passes every existing gate, and the 500-comment fixtures pass decision 9's gate.

## Risks

- **A position that changes the PDF.** The largest risk. The facts above come from reading the source; facts 7 and 8 are not proved. Step A is first for this reason. If a "Yes" row fails, the row becomes "No" and the anchor snaps outward; the format itself does not depend on any one row.
- **A lost `*/`.** Fact 2: if two characters of a start marker or an end marker are deleted in another editor, the rest of the document can become a comment with no error. Prose cannot prevent this in a file it does not edit. In Prose, decision 4 stops single keys from deleting either one, and the index reports "Not closed". This risk is the same for every Typst file with a block comment, and it is the cost of anchors inside a paragraph.
- **The text-change gate.** Rewriting an edit, or adding a second edit to its undo group, in `shouldChangeText` touches the path that typing, IME and undo use. Phase 3's IME and undo tests must pass unchanged, and the rules do not run while text is marked.
- **Moving the column.** The second gutter layout moves the text column left. If that invalidates layout for the document, a book pays for it. Step D measures it; the fallback is the third layout (icons and popovers) whenever the centred column has no room.
- **Find.** A phrase across a start marker or an end marker is not found. A writer who comments heavily will meet this.
- **The formatter and other tools.** A formatter may move a block comment or join lines. Step A shows what the bundled one does. Other tools are outside Prose's control; decision 3's table is the answer.
- **Scroll cost.** The overlay moves cards on every scroll frame. With many cards in view this is view layout on the main thread. The scroll gate in the benchmark covers it.
- **Two meanings of "comment".** The existing `comment` command (`⌘/`) makes a source comment. Titles must keep them apart: the old command becomes "Toggle Source Comment" in the panel.
